# Production bootstrap ownership

This separate Terraform root owns one private evidence bucket and one production Terraform OIDC role from creation. Both flags default to false. Enabling both declares exactly eight managed resources: six S3 resources and the role plus its inline policy. It creates no application prerequisites or serving changes.

No live initialization, plan, Apply, IAM change or upload is authorized by adding this source. Provisioning needs its own reviewed private operation packet. Keep account, key, administrator, reviewer and other resource bindings in that packet, outside this publishable tree.

## Ownership and inputs

The S3 backend uses `meeting-notes-terraform/production-bootstrap/state` in the existing state bucket, with the existing DynamoDB lock table. The application state key remains `meeting-notes-terraform/state`. Only the default workspace is accepted. Never add this root as a parent module, import its resources into the application state, migrate the old state-management stack or override the backend key.

Required enabled inputs name the independently verified production account, existing enabled KMS key, administrator and private reviewer roles. The same administrator may perform the human review when explicitly selected in the private packet. Neither identity may be the Terraform executor or either runtime role. The role also requires independently verified numeric GitHub repository/owner IDs, the production API certificate ARN and hosted zone ID. No private bindings have public defaults.

Trust fixes the existing GitHub provider, `sts.amazonaws.com`, `repo:Chronote-gg/Chronote:environment:production`, `refs/heads/master`, both numeric IDs and a one-hour maximum. Native OIDC acceptance remains a later prerequisite. Plan and Apply share this role; Plan must receive the separately reviewed read/lock/capture-only session restriction. Trusted production workflows can otherwise request the base permissions.

All eight resources have `prevent_destroy`; the bucket also has `force_destroy = false`. Default off prevents installation, it does not authorize removal after installation. Keep the flags enabled once provisioned. An interrupted Apply can leave a subset of the resources. Reconcile read-only, then review a new saved plan. Never retry an uncertain creation or delete partial resources as compensation. In particular, us-east-1 CreateBucket has special behavior for already-owned names, so prove absence before the first operation.

## Evidence controls and limits

The bucket uses BucketOwnerEnforced, all public-access blocks, versioning and the existing SSE-KMS key with bucket keys disabled. There is no expiration, lifecycle resource, Object Lock, replication or new key. It denies insecure transport and unapproved principals. Capture writes require `If-None-Match: *`, explicit SSE-KMS and the exact key header. The Terraform role can put and read exact versions only under `terraform/production/*`, and read the controls required by the existing capture adapter. It cannot delete evidence, read the latest object or administer storage. Introduction and collector grants require later reviewed policy changes.

Administrator maintenance remains separate from capture permissions. If the administrator also reviews evidence, its existing administration rights remain. Versioning does not prevent administrator or account-root deletion. The private packet must fix administrator trust, private reviewer route, exact policy byte hashes, the lifecycle hash of `JSON.stringify(null)` and retention covering at least six hours from each invocation. Ongoing versions and KMS requests incur costs. A distinct reviewer would also need its own existing-key decrypt permission, which this root does not create.

The Terraform role never owns or changes the evidence bucket/key, its own role/policy/trust, an ECS service/task or a listener. It receives no PassRole, customer table content read or secret-value read permission. Reading the exact application state can still reveal sensitive values, and requires explicit protected-operation approval. The supplied private metadata reports AES256 for that exact existing state object; a bucket encryption default alone would not prove this. Recheck exact-object metadata before execution. Do not add guessed state-key decrypt permission.

Two IAM limits require trusted saved-plan validation. IAM cannot constrain PutRolePolicy's submitted inline name or body, so this privilege can change other inline permissions on the runtime role. CreateTargetGroup offers no VPC condition; its name-scoped ARN does not enforce the chosen VPC, protocol or health settings. The four-target validator and protected source must enforce these values. Do not claim IAM enforces them. The runtime grant adds the same limit for both new roles: IAM cannot constrain the submitted trust or inline documents, so CreateRole and PutRolePolicy there are as strong as the protected source and `validate-runtime-plan.cjs`, which binds addresses, actions and the two in-place changes.

The pinned IAM policy update path prunes the oldest non-default version only when five versions already exist. The long-lived task-role DynamoDB policy may already be at that limit, so DeletePolicyVersion is granted for that policy alone. A routing policy update at the limit must still stop for a separately reviewed permission change. The rendered policy is close to the 10,240 character inline limit; check its size before adding statements. Native effective permissions, service grants and exact dependency/refresh acceptance remain unproved until the separately approved operation. Missing privilege is a blocker, not a reason to add broad ReadOnlyAccess or AdministratorAccess. The full application root can initialize other provider configurations; this AWS-only root does not settle their credentials or authority.

## Private saved-plan review

Before any live operation, the packet must fix the administrator session, source SHA, Terraform/provider versions, lock hash, exact inputs, new backend key, expiry and Windows ACL-protected output directory. Prove bucket/role/new-state absence from metadata; AccessDenied is UNKNOWN. Verify state and lock-table metadata/access without reading application state. Approve private backend initialization and Plan separately from Apply.

Use the existing `scripts/deployment/terraform-process.cjs` `runPrivateCommand` to preserve complete stdout/stderr privately. Its POSIX file mode does not prove Windows ACL privacy. Never print its returned base64 streams or use public Actions artifacts. Do not add a fallback to the normal private runner: it must still refuse absent/unreadable evidence storage.

`verify-plan.cjs` is only an offline action/document guard. It reads a private `terraform show -json` document and a separately reviewed binding JSON, then checks exactly the eight create actions, known controls and exact policy bytes. The binding has `backendKey`, `variables` (the complete exact plan variable map), and `policySha256` with `bucket`, `trust`, `role` lowercase SHA256 values for the exact policy strings. No replacement, import, move, extra managed resource, unapproved data read, drift or deferred work is accepted.

The guard cannot prove backend selection, source identity, human approval or the relation between a JSON rendering and its saved binary. Terraform JSON omits backend configuration. The operation packet and protected capture must bind source/configuration, actual initialized backend, lockfile, inputs, private JSON/rendered review and saved binary hashes separately. A handwritten matching JSON is not Apply authority. Initial review requires exactly eight creates; later no-change readback uses separate review, not a weakened initial guard.

After explicit approval of the exact saved plan, apply those saved bytes once, without replanning. Preserve local evidence if upload or acknowledgment fails. Later approval must test conditional capture, exact version/hash/encryption, effective denials and actual OIDC assumptions. A no-change plan proves readback/ownership, not application runtime acceptance. The four application prerequisites, workflow bindings, production protection, retention promise and cutover each retain their own gates.

## Offline checks

From the repository root, use the existing cached provider without initializing S3:

```powershell
terraform '-chdir=_infra/production-bootstrap' init -backend=false -lockfile=readonly '-plugin-dir=../.terraform/providers'
terraform '-chdir=_infra/production-bootstrap' fmt -check -recursive
terraform '-chdir=_infra/production-bootstrap' validate
terraform '-chdir=_infra/production-bootstrap' test -no-color '-filter=tests\bootstrap.tftest.hcl'
$env:BOOTSTRAP_MOCK_PLAN_JSONL = Join-Path $env:TEMP 'bootstrap-mock-plans.jsonl'
$mockRaw = Join-Path $env:TEMP 'bootstrap-mock-raw.jsonl'
terraform '-chdir=_infra/production-bootstrap' test -no-color -json -verbose '-filter=tests\guard-plan.tftest.hcl' > $mockRaw
node _infra/production-bootstrap/compact-mock-plan.cjs $mockRaw > $env:BOOTSTRAP_MOCK_PLAN_JSONL
node --test _infra/production-bootstrap/verify-plan.test.cjs
```

The single-run guard fixture limits verbose output to one plan. The compactor retains only its resource changes and outputs, excluding repeated provider schemas. All fixture identities are synthetic.

The Checkov job in `ci-core.yml` pins Terraform 1.16.0 and runs these checks, including the guard against the actual eight mocked resource changes and rendered policies. Terraform's mock JSON omits the reviewed variable/configuration envelope, so that integration test supplies a synthetic envelope. It proves compatibility with this root's rendered resources and policies, not a saved binary plan, backend access or live permissions. A direct Node run without `BOOTSTRAP_MOCK_PLAN_JSONL` skips that integration case and runs only the synthetic regressions.

The guard checks resource type/name/index consistency, exact allowed data identities and completed identity fields. It refuses configured embedded S3 controls, role attachments and inline policies, while allowing unconfigured provider-computed defaults. Policy checks require a nonempty object with the emitted IAM version and statement structure, including mutually exclusive Action/NotAction and Resource/NotResource. Exact reviewed hashes remain the authority for policy meaning.

To check already-approved local renderings offline: `node _infra/production-bootstrap/verify-plan.cjs <private-plan.json> <reviewed-binding.json>`. This command makes no network call or provider invocation.
