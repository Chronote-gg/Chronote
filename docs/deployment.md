# Deployment

How a backend deployment works, what an operator watches, and what to do when something goes wrong. The design and its trade-offs are recorded in [the lifecycle simplification ADR](adr-20261111-lifecycle-simplification.md). Every duration below comes from `LIFECYCLE` in `src/services/lifecycleTiming.ts` or from `scripts/deployment/deploy.cjs`; this page explains only the ones an operator acts on.

## Workers

Every ECS task runs the same worker. A worker writes one registry item to the deployment control table under partition `WORKERS` (sort key `WORKER#<instanceId>`) and refreshes it on a 10 second heartbeat. The item carries the instance id, `release`, `ready`, `heartbeatAt`, the number of live captures and finishes, `protectedUntil` and the task ARN.

- `release` is the ECS task definition revision, read from the task metadata endpoint. Outside ECS it comes from `WORKER_RELEASE` and defaults to 0.
- `ready` is true while the Discord gateway is connected, the web server is listening and the worker has read the registry at least once. It is live: a worker that loses its gateway connection stops being ready until it reconnects.
- A worker is **eligible** when it is ready, is not shutting down, and no other worker with a heartbeat in the last 30 seconds is ready on a higher release. Workers on the same release are all eligible.

Only eligible workers start meetings, answer general commands, and run the shared background jobs (the finisher, processing retry, personal uploads, meeting update delivery, renewal recovery). A worker that is not eligible is **draining**: it keeps recording the meetings it already holds, and it polls only for control commands addressed to it while it holds one. It takes nothing new. Every worker receives every interaction, and the lease decides which one acts: the end button, `/leave` and **Stop recording** reach the worker holding the server's live lease, and so do the interactions that read the live session (`/say`, `/tts`, tag edits, image generation). With no live lease, an end control gets the reply `The recording has ended. Notes will follow.` from one eligible worker, and a session interaction runs its normal handler there. Exactly one worker answers each interaction: it first claims the interaction receipt, and a worker that does not hold the receipt never responds. A control command addressed to a worker that has left the registry is answered by an eligible worker from the lease: it is left for its holder while the lease is live, and otherwise a stop is answered as ended.

Each eligible worker logs `Worker eligible heartbeat` at most once a minute. The `no_eligible_worker` alarm watches that line. Each finisher scan that reads the table through logs `Meeting finisher scan completed`, at most once a minute per worker, and the `finisher_scan_missing` alarm watches that one.

`/health` returns 200 once the worker's first `ready: true` registry write has succeeded and stays 200 after that, so a later Discord outage does not make ECS replace the task. Before that it fails, so the load balancer sends no traffic to a booting task and ECS does not stop the old task early. The service's health check grace period is 300 seconds, set by Terraform and by every rollout.

### Why meetings can start during a deployment

The old worker stays eligible until a worker on the new release is ready. At that moment the old worker becomes draining and the new one takes every new start, so there is no moment when nobody accepts a start. If the new worker never becomes ready, the old one keeps serving and ECS never stops it. For up to one heartbeat both workers may be eligible; the per-server lease decides which one records.

A meeting that is being recorded stays on the worker recording it until it ends. When a draining worker ends a capture, it leaves the meeting's processing to an eligible worker, which finishes it from what was saved to S3. Those notes match a normal finish, but the meeting has no raw chat log object and its final transcription pass runs on a mix rendered from the saved pieces. An auto-recording finished that way still gets the automatic cancellation check when it had no chat messages, but with the default cancellation model, not a server's override; an auto-recording with chat messages proceeds to notes.

While an old worker drains, both tasks are in the target group, so some portal requests reach the older code, and a live transcript page served by the worker that is not recording shows status only.

### Shutdown

On SIGTERM a worker runs its shutdown in stages (`src/services/workerShutdown.ts`). Each stage is bounded, and the worker exits within 90 seconds; ECS stops the container 120 seconds after SIGTERM.

1. It writes `ready: false` to its registry item (3 seconds). Other workers stop treating it as ready at their next registry read, and `wait-ready` no longer counts it; the protection wait in `wait-drain` looks at heartbeat freshness and live captures, not at `ready`.
2. It stops its pollers, the finisher loop and the local sweep, and waits for a start in progress, which the shutdown signal aborts, to release its lease (3 seconds).
3. It closes each live capture as interrupted: leaves voice, flushes for at most 45 seconds (less when the deadline is nearer), makes one capture-end write without a finish claim, and releases the lease. This stage gets whatever the others leave, at least 65 seconds. Audio not flushed in time is lost, and the meeting is finished from what reached S3.
4. It aborts the finish attempts it is running, waits up to 5 seconds for them to stop, and hands their claims back without counting an attempt (8 seconds).
5. It drains in-flight billing operations, releases the renewal recovery lease and waits for a personal upload poll in progress (3 seconds). A personal upload it had claimed is retried by an eligible worker once the claim lapses, at the cost of one of its three attempts.
6. It closes the web server and the Discord client (3 seconds), then flushes telemetry and exits.

An eligible worker picks up those meetings on its next finisher scan. A worker that dies without SIGTERM is handled the same way: its captures end at their last saved piece and its claims become reclaimable after two minutes. A capture whose worker died is adopted once neither its lease nor its saved audio has moved for two minutes. Its duration comes from the end its checkpoint confirms, or, when the exact coverage is unknown, from an estimate based on the saved audio pieces; in that case the notes say the exact end time is unknown, the portal and Notion show the duration as unknown, and the weekly limit counts the estimate, which can be short by up to one 30 second piece per speaker. A worker that dies before its first piece is saved, within about 30 seconds of the first speech, leaves the meeting `failed` with nothing posted.

## Task protection

Protection covers captures only, never processing.

- Before joining voice for a recording, a worker asks ECS for task protection that expires 10 minutes after the latest moment any of its leases may be renewed. A lease is never renewed past the meeting duration cap (2 hours) plus 15 minutes, so protection for a meeting ends at most 145 minutes after that meeting started.
- While a capture is live and the call has not succeeded, the worker retries once a minute. It publishes the confirmed expiry as `protectedUntil` in its registry item.
- It never extends protection without an unexpired lease, whatever the process believes about its captures.
- When its last capture closes it clears protection, retrying until the call succeeds.
- A refused or failed call logs `Task protection failed during capture` and is counted. It is never a reason to stop a meeting or a worker.

Protection is what makes ECS keep a draining task alive. Because it always expires on its own, ECS bounds every drain without help from the worker. Platform retirement, a failed health check and `StopTask` can still stop any task; its meetings are then finished like any other abandoned capture.

## The deploy job

`deploy.yml` deploys production on every push to `master` and on dispatch. `deploy-staging.yml` deploys Sandbox on dispatch only. Both run a **Deploy Backend** job that calls `scripts/deployment/deploy.cjs` in this order:

| Step         | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Bound                       |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `wait-drain` | Waits until no RUNNING task of the service is on a task definition other than the service's current one. Such a task is usually an older worker draining a live recording; it can also be one ECS has not finished stopping, or one that cannot clear its protection, which always expires by itself. It first reads the cutover marker; before the cutover it behaves differently (see [the first deployment](#first-deployment-of-the-worker-design)). Then waits for every worker with a fresh heartbeat and a live capture to report `protectedUntil` in the future, and proceeds whether or not they do. | 160 minutes, then 5 minutes |
| (image)      | Refreshes the AWS session (the drain wait can outlast most of one), then builds and pushes the image, pinned by digest.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |                             |
| `preflight`  | Checks that the service exists and is ACTIVE and, when it has a load balancer, that the listener named by `DEPLOYMENT_LISTENER_ARN` sends full weight to the target group the service is bound to. Changes nothing.                                                                                                                                                                                                                                                                                                                                                                                           |                             |
| `rollout`    | Takes the family's latest ACTIVE task definition, removes `DEPLOYMENT_CANDIDATE_ID`, sets the new image, registers a new revision and updates the service with minimum 100 percent, maximum 200 percent, the circuit breaker off, early success with deferred cleanup of the old revision, and a 300 second grace period. Prints the previous image before the update.                                                                                                                                                                                                                                        |                             |
| `wait-ready` | Waits for a registry item on the new revision that is ready with a heartbeat in the last 30 seconds.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | 15 minutes                  |
| `rollback`   | Runs only when `rollout` or `wait-ready` failed and the previous image is known. It first reads the cutover marker. With the marker present: if the service never left the previous image it changes nothing, otherwise it registers another revision with the previous image and updates the service. With the marker absent or unreadable it changes nothing. The run fails either way.                                                                                                                                                                                                                     |                             |

The script never changes the load balancer binding, the listener or the desired count. Task definition revisions only ever increase. On success the post-deploy jobs run (frontend publication, and in production prompt promotion and the OpenAI connection sync). The old task drains on its own and the workflow does not wait for it.

### One deployment at a time

The backend job holds the concurrency group `backend-rollout-production` (Sandbox: `backend-rollout-sandbox`) with `cancel-in-progress: false`, and the drain wait and the rollout run inside that one job, so no other run can roll out between them. GitHub keeps one pending job per group and cancels the older pending one, so when several runs queue, the newest commit is the one that deploys. The job times out at 240 minutes.

A deployment that arrives while an older worker drains therefore waits for that worker's live meeting, up to the length of a meeting. That is the only wait that depends on a meeting; the others are the five minute protection wait, the 15 minute ready wait and the environment approval.

### Skipping the drain wait

The `retire_older_tasks` dispatch input (ignored on push runs) makes `wait-drain` stop each older-revision task with `StopTask` instead of waiting for it. Their live meetings end at their last saved piece, audio not yet uploaded is lost, and an eligible worker finishes them from S3; their notes say the recording ended unexpectedly. Use it only when a fix cannot wait for a live recording to end. Only the owner dispatches or approves a run with `retire_older_tasks`. Before the cutover it stops nothing (see [the first deployment](#first-deployment-of-the-worker-design)).

The deploy role may call `StopTask` only when `TFVAR_ENABLE_DEPLOY_RETIRE=true` has been applied. Without that, a dispatch with `retire_older_tasks` fails at its first stop. An operator `StopTask` on the older task, followed by an ordinary dispatch, has the same effect. In Sandbox `retire_older_tasks` fails at its first stop until the [Sandbox gap](#sandbox-gap) is closed.

### Failures, cancellations and rollback

- **Drain timeout.** `wait-drain` publishes `DrainWaitTimedOut` and fails the run before the image is built. Nothing changed. See the `deploy_drain_timeout` alarm below.
- **Preflight failure.** Nothing changed. The listener and the service binding disagree; correct that through a reviewed change before deploying again.
- **Rollout or ready failure.** The rollback step runs and the run fails. The old worker never stopped accepting meetings, because it stays eligible until a newer worker is ready. When the cutover marker is absent or unreadable, rollback changes nothing; see [the first deployment](#if-the-new-worker-never-becomes-ready).
- **Cancelled or timed-out job.** There is no rollback: the rollback step's condition is `failure()`, which is false for a cancellation, including a timeout. If the job stopped after `update-service`, the service stays on the new revision and nobody waits for readiness. ECS still keeps the old task until the new one passes its health check. Check the registry and the new task's logs, then deploy again or deploy the earlier commit.
- **Rolling back on purpose** means deploying the earlier code again (in production, by reverting on `master`, because the production deploy role trusts only `refs/heads/master`). That registers a higher revision. Pointing the service at a lower revision by hand is not supported.
- **Never re-run a deploy run from before the lifecycle simplification.** A re-run uses that run's own workflow file, which still calls the deleted coordinator.

### Terraform Apply during a deployment

Production Terraform Apply refuses while any `deploy.yml` run is in progress, queued, waiting or pending (`productionWriters` in `scripts/deployment/terraform-native.cjs`). A deploy can hold its backend job for up to about four hours (160 minutes of drain wait, 5 minutes of protection wait, the build, and up to 15 minutes of ready wait), and Apply stays refused for all of it. The check is a snapshot, not a lock: a deploy that starts after it can still overlap the Apply, so avoid merging while an approved Apply is running.

### Changing a Terraform-managed environment variable

It takes three steps, and the third is the one people miss: set the value, apply, then deploy. Terraform apply registers a new task definition revision, but `aws_ecs_service` sets `ignore_changes = [task_definition]`, so the service keeps running the old revision. `rollout` builds its new revision from the family's latest ACTIVE revision, which is Terraform's, so a deploy is what carries the change to the running worker.

### Sandbox gap

No Sandbox Terraform Plan/Apply scope carries the deploy role's `PutMetricData` and `StopTask` statements: `deployment-runtime` covers production only, and Sandbox refuses `full`. Until then, in Sandbox a drain timeout fails on the metric call with an access error, the drain timeout alarm cannot fire, and `retire_older_tasks` fails at its first stop, so a Sandbox rehearsal cannot exercise retire or the drain alarm. The owner still has to decide whether to add a Sandbox scope for those statements or apply them another reviewed way.

## First deployment of the worker design

The first deployment replaces a task that still runs the old deployment protocol. The two must never process the same meeting. A new worker reads old state in exactly one place: while any old runtime record (partition `ENV`, sort key `RUNTIME#...` in the deployment control table) has a heartbeat newer than two minutes, or while those records cannot be read, it is ready but **not eligible**. In that standby it takes no meetings, runs no finisher and never asks for protection. That check is removed in the following release.

Until the cutover marker exists, the deploy script behaves differently too. `wait-drain` and `rollback` both start by reading the marker from the registry in `DEPLOYMENT_CONTROL_TABLE`, with up to three tries (`Cutover marker read <n> of 3 failed: ...`).

`wait-drain` then handles four cases:

- **Marker absent.** Older tasks are not waited for, because the older task is the old runtime. It logs `Cutover marker absent: the old runtime is still in charge and is not waited for`. With `retire_older_tasks` it also logs `Cutover marker absent: retire is not available before the cutover`, stops nothing and does not fail. Because older tasks are not waited for, a second attempt is not held for 160 minutes.
- **Marker unreadable, without retire.** It logs `Cutover marker could not be read; waiting for older tasks as after the cutover` and waits for older tasks. Before the cutover that means waiting on the old runtime for up to 160 minutes and then failing with the drain alarm. An operator who sees that message during the first deployment cancels the run and dispatches again, and the new run goes through steps 6 and 7 again (the approval order and the idle check).
- **Marker unreadable, with retire.** Nothing is stopped and the step fails: `Cutover marker unreadable: the cutover state could not be read, so retiring older tasks was refused and nothing was stopped`.
- **Marker present.** The normal behaviour.

`rollback` before the cutover changes nothing in ECS. The old image cannot be rolled back to: a revision registered from the new task definition has no candidate id, and the old code refuses to start without one. With the marker absent it fails with `Cutover marker absent: the old runtime is still in charge. Nothing was rolled back: the service still points at the revision that failed and the old runtime's task was not touched. Fix forward with a new deployment of a fixed commit, never a rollback, and do not stop the old task until a new worker reports ready; failing the run`. With the marker unreadable it fails with `Cutover marker unreadable: the cutover state could not be read, so nothing was changed. If the cutover has already happened, roll back by redeploying the last good commit; failing the run`.

### The old runtime may stop by itself

During a deployment ECS can refuse the outgoing task's protection renewals. The old runtime renews a ten minute protection every minute and logs `Runtime protection renewal failed` for each refusal. About eight minutes after its last successful renewal it closes admission, takes no new meetings and preserves what it holds; its protection lapses about two minutes later, and ECS can then stop it. So the old task may stop at a moment nobody chose. If it does, the cutover proceeds without the manual stop. This is why the backend job is approved only when no meeting is live and the stop follows as soon as the new worker is ready. That interval is not short: it includes the protection wait of up to five minutes, the image build, `preflight`, `rollout`, the new task's start and up to fifteen minutes of `wait-ready`, and the old runtime accepts meetings throughout. A meeting live on the old task when it stops is cut, and from the admission close until the cutover nobody takes meetings.

Whether ECS refuses those renewals while the new worker stands by without protection is **not verified**. The Sandbox rehearsal must answer it.

### Procedure

Rehearse the whole procedure in Sandbox first, within the limits of the [Sandbox gap](#sandbox-gap). The rehearsal must answer these before the production run:

- The old runtime writes a fresh `ENV` / `RUNTIME#...` heartbeat, the new worker stands by while it does, and the new worker writes the cutover marker and logs `Worker eligible heartbeat` about two minutes after the old task stops.
- Whether the old runtime's task is protected at the moment of the deployment. If it is not, ECS can stop it as soon as the new task is healthy rather than at the idle moment step 9 chooses.
- Whether ECS refuses the old runtime's protection renewals while the new worker stands by without protection (watch for `Runtime protection renewal failed`).
- A simulated failed first deployment, with a new worker that never becomes ready: the old runtime keeps serving, ECS does not stop it, rollback changes nothing, and a second attempt is not held by the drain wait.
- `update-service` with the grace period accepted on the service as Sandbox runs it, and whether the first Terraform plan after the change shows a diff for the deployment circuit breaker or the early-success settings.
- One `no_eligible_worker` and one `finisher_scan_missing` ALARM and OK pair arrive as step 5 describes, and both alarms' timing holds up against log ingestion delay.
- Whether the `sandbox` GitHub environment requires approval, so the approval order in steps 6 and 7 can be rehearsed as written.

1. **Confirm the inputs.** `DEPLOYMENT_LISTENER_ARN` is set in the target GitHub environment. `DEPLOYMENT_CONTROL_TABLE`, or its default `<SECRETS_PREFIX>-DeploymentControlTable`, names the application's deployment control table in both production and Sandbox: the script reads the cutover marker and the worker registry from it. Decide whether `TFVAR_ENABLE_DEPLOY_RETIRE` should be `true`.
2. **Confirm the old runtime writes a fresh `ENV` / `RUNTIME#...` heartbeat.** If no such record exists, the new worker does not stand by and becomes eligible at once, alongside the old runtime. Stop and take it to the owner; do not dispatch.
3. **Merge without deploying yet.** A merge to `master` starts `deploy.yml`. Until you are ready to do the first deployment, reject that run's backend job at its production environment approval, or cancel the run before the backend job starts. The first deployment is a later run, approved at a moment a person chooses.
4. **Apply Terraform, immediately before the deployment run.** Production: first the owner applies the `_infra/production-bootstrap` root, whose processing retry policy grants the Terraform role the lifecycle and drain alarm names (the role cannot update its own policy, so this is a separate administrator Apply, as that root's README describes); then a `processing-retry` scoped Plan, then its Apply (the lifecycle and drain alarms); and a `deployment-runtime` scoped Plan and Apply (the deploy role's `PutMetricData` grant and, if enabled, `StopTask`). Sandbox: a `processing-retry` scoped Plan and Apply for the alarms; the deploy role statements have no Sandbox route (see the [Sandbox gap](#sandbox-gap)). The health check grace period needs no apply. Apply refuses while any `deploy.yml` run is pending, which is why step 3 comes first.
5. **Expect `no_eligible_worker` and `finisher_scan_missing` to fire.** The old runtime logs neither `Worker eligible heartbeat` nor `Meeting finisher scan completed`, so `no_eligible_worker` fires within about five minutes of the apply and `finisher_scan_missing` within about ten, and both stay firing until the cutover. Expect two ALARM emails and two OK emails.
6. **Start the run and wait for the backend approval request.** At a quiet hour, dispatch `deploy.yml` (without `retire_older_tasks`), or let a merge start it. Approve `deploy-docs`, which needs its own `production` approval. The backend job asks for approval only after `ci` and `deploy-docs` finish. Do not run the idle check before this point: a check made before dispatch is a whole CI run old by the time the backend asks.
7. **Check that the old runtime is idle, then approve the backend job at once.** If any check fails, do not approve; wait and check again. All of these must hold at once:
   - `ActiveMeetingTable` has no item whose `leaseExpiresAt` is in the future. The old runtime holds a meeting's lease until its processing ends, so this check is the authority for "no meeting is live or being processed".
   - `MeetingControlCommandTable` has no item with `queueStatus` `pending` and `expiresAt` in the future. These commands are short-lived, so waiting a minute clears them.
   - As a secondary sign, the old task's logs show no recent `Meeting end step completed:` lines without a following `save-meeting-history` step. These lines carry no meeting identifier, and a long transcription can go minutes without one, so they do not replace the lease check. A meeting the old runtime is still processing when it stops is **not** finished automatically, because rows from before this change are finished only by an operator decision. It must be absent, or the operator must be ready to finish it with the [stranded-meetings commands](#stranded-meetings).
   - `PersonalMediaUploadJob` has no job whose claim (`claimExpiresAt`) is still in the future. A claimed job can be accepted instead: once its claim expires an eligible worker claims it again and retries it, at the cost of one of its three processing attempts.
   - `PersonalRecordingSegment` has no segment written in the last few minutes, which would mean a desktop recording is uploading right now.
8. **Let the backend job run.** `wait-drain` logs that the old runtime is not waited for and `rollout` updates the service. The new worker boots, becomes ready, and stands by. `/health` returns 200 and `wait-ready` succeeds, so the run turns green while the old runtime is still the one taking meetings. Watch the old task's logs for `Runtime protection renewal failed`.
9. **Repeat the idle check, then stop the old task with one `StopTask`,** as soon as `wait-ready` succeeds. If the check fails, do not stop the old task: wait and check again. The new worker stays in standby and nothing is lost by waiting, unless `Runtime protection renewal failed` appears in the old task's log; then the old runtime closes admission about eight minutes after its last successful renewal, so make the stop at the first idle moment. The old task is the one running the pre-change image, which is the lowest task definition revision among the service's running tasks. After a failed first attempt a task on the failed revision can also be running, so check each task's task definition revision and image in the ECS console or with `aws ecs describe-tasks` before stopping. This step is not optional: until the old task is stopped, it could process a meeting the new worker also processes, which would post notes twice. If the old task already stopped by itself, there is nothing to stop.
10. **Wait for cutover.** 120 seconds after the old runtime's last heartbeat, the new worker writes the permanent cutover marker (`WORKERS` / `CUTOVER`) on its next heartbeat and becomes eligible. Confirm `Worker eligible heartbeat` in its logs and the `no_eligible_worker` OK email; the `finisher_scan_missing` OK email follows once its first scans complete. The old runtime can keep heartbeating through its shutdown window, so the gap from the stop until the cutover is about two to four minutes. In it nobody takes meetings and commands get no answer. This gap happens once.

After cutover:

- No worker ever enters standby again, whatever the old records say.
- Old voice records are ignored, so a server that one of them locked out can start meetings again.
- The finisher touches only rows written by this design, so nothing left over from the old runtime is processed or posted automatically.
- The normal rollback applies: a higher revision with the previous image.
- **There is no return to the old protocol.** Never deploy an image built before this change. If the new worker is unhealthy, ship a fix: the deploy path cannot be blocked by a meeting, a lease or local state.

### If the new worker never becomes ready

When `wait-ready` fails before the cutover, nothing is rolled back or stopped. The service points at the failed revision and ECS keeps trying to start it. Never stop the old task until a new worker reports ready.

The old runtime keeps serving as long as its protection renewals succeed. Whether they do while ECS is retrying the failed revision is not verified. Watch the old task's log for `Runtime protection renewal failed`. If it appears, the old runtime closes admission about eight minutes after its last successful renewal, and nobody takes new meetings until a fixed worker is ready and the cutover happens, so the fix-forward becomes urgent.

Fix forward with a run of a fixed commit, ordered the same way as the first attempt: dispatch it or let its merge start it, approve `deploy-docs`, wait for the backend job's approval request, run the idle check (step 7), and approve. This run **is** approved: step 3's instruction to hold or reject a merge's run applies only until the operator is ready to do the first deployment. Then continue from step 8.

## Stranded meetings

Meetings left unfinished by the old runtime do not carry `lifecycleVersion: 2`, so the finisher never touches them. They are finished only by an operator decision, one meeting at a time, never automatically.

Both commands run through `yarn meetings:stranded` (`scripts/stranded-meetings.ts`).

- `yarn meetings:stranded list --out <new directory>` finds every row without the marker whose status is `starting`, `in_progress` or `processing` and writes `stranded.json` into a new owner-only directory, which must be outside every Git checkout (created through `scripts/privateOutput.ts`; an existing path is refused). Each entry carries the meeting's key, status, whether its transcript and notes are saved, whether a live lease still names it, and what its checkpoint manifest claims (artifact counts and, when verified, the saved duration). It reads manifests only and never downloads audio. The terminal shows only the count, `{"stranded":<n>}`. A terminal row left with a finish map by an earlier `finish` run whose delivery did not complete (`delivery_pending`) is not listed; `finish` still accepts it by key.
- `yarn meetings:stranded finish <guildId> <channelId_timestamp> --post` claims the meeting as an operator (a meeting still marked as recording is adopted as interrupted), rebuilds its input from the history row and the saved checkpoint with the recovery loader, runs the normal finish pipeline and delivers the notes to Discord.
- `yarn meetings:stranded finish <guildId> <channelId_timestamp> --no-post` does the same without posting anything to Discord. The meeting is otherwise finished as normal, so the Notion export automation and the completion analytics event still run. The row is left settled and unpublished: the portal's retry and later notes corrections work by their normal rules (corrections are stored, not sent to Discord), and a leftover recovery value from the old runtime is removed from the row. Exactly one of `--post` or `--no-post` is required.

`finish` refuses a meeting whose live lease still names it: the old runtime holds a meeting's lease until its processing ends, so something is still working on it. It retries in its own process, on the pipeline's backoff, for at most three attempts, so it never leaves a retry for anything else to pick up. When it still cannot finish, or on Ctrl-C, it puts a row that still needs processing back exactly as it found it. A meeting whose notes were already saved keeps them and its final status, and only its claim is released.

It prints one line, `{"result":"<result>","deliver":<true|false>}`, and for the results that leave the meeting unfinished an explanation on stderr. Only `finished` exits 0; every other result exits 1.

| Result             | Meaning                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `finished`         | The meeting reached its final status and, with `--post`, was delivered.                                                  |
| `failed`           | The meeting ended `failed`: it has no saved audio, or processing gave up after its retries.                              |
| `delivery_failed`  | With `--post`, the notes are saved but delivery was recorded as failed.                                                  |
| `delivery_pending` | The notes are saved and the status is final, but delivery did not complete. The claim was released; rerun with `--post`. |
| `restored`         | The meeting could not be finished, and its row was put back as it was.                                                   |
| `interrupted`      | Ctrl-C stopped the attempt, and the row was put back as it was.                                                          |
| `restore_refused`  | The row could not be put back because another claim holds it or it changed. It was left as it is.                        |
| `lease_held`       | A live lease names the meeting. Nothing was changed.                                                                     |
| `not_claimable`    | No claim could be taken (another claim holds the row, or it changed since it was read). Nothing was changed.             |
| `not_stranded`     | The row carries the marker, or it is terminal with no finish in progress. A marked row belongs to the finisher.          |
| `not_found`        | No row has that key.                                                                                                     |

Use `--no-post` when a post would surprise the server now (an old meeting, a channel that moved on) or while customer contact is still being decided; the notes are then visible in the portal only. Use `--post` when the owner has decided the server should receive the notes.

Run them like `scripts/retry-meeting-processing.ts`: with a full app environment and the target environment's AWS credentials, under the existing production approval rules. The list of affected meetings, each decision and any customer contact belong in the private operations repository and need the owner's authorization. Never paste meeting identifiers or content into public issues or logs.
